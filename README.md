# 와탭랩스 사용자 파일 API

Spring Boot로 사용자 파일을 메모리에 적재하고 조회·검색·파싱 실패 확인·재적재 API를 제공합니다.

## 1. 실행 방법

- 환경: Java 21, DB·Docker 불필요
- 실행 위치: 프로젝트 루트 / 기본 포트: 8080
- 기본 입력: 작업 디렉터리의 `user.txt` — 제공 원본 포함, 정상 37건·실패 3건
- 입력 파일은 JAR에 미포함 — JAR 실행 시에도 외부 파일 필요

실행 전 `java -version`으로 Java 21 사용 여부를 확인하세요. JDK 21이 없다면 먼저 설치해야 합니다.
macOS에서 JDK 21이 설치되어 있지만 다른 버전이 선택된 경우, 현재 터미널에서 설정합니다.

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
```

```bash
./gradlew bootRun
# 다른 파일을 사용할 경우
USER_FILE=/absolute/path/user.txt ./gradlew bootRun
```

**API 문서**

- 실행 후 [Swagger UI](http://localhost:8080/docs/swagger-ui.html): API 직접 호출 / [REST Docs](http://localhost:8080/docs/index.html): 요청·응답 예시
- `bootRun`·`clean build`: 테스트 결과로 문서 생성, 실행 JAR에도 포함
- 문서만 생성: `./gradlew apiDocs`

## 2. API

| 메서드·경로 | 기능·입력 | 성공 응답 (200, JSON) |
| --- | --- | --- |
| GET /users?page=0&size=20 | 전체 사용자 페이지 조회 | content, page, size, totalElements, totalPages |
| GET /users/{id} | ID로 사용자 조회 | id, name, age, gender, salary |
| GET /users/search?name=다 | 이름 부분 문자열 검색 | 사용자 배열 |
| GET /users/parse-errors | 파싱 실패 조회 | 행 번호(lineNumber), 원문(rawLine), 사유(reason) 배열 |
| POST /users/reload | 파일 재적재, 요청 본문 없음 | loadedCount, failedCount |

- 오류 형식: `code/message`
- 400: 잘못된 입력 / 404: 없는 사용자 / 503: 재적재 파일 읽기 실패 / 500: 예상하지 못한 오류

## 3. 파일 적재 및 오류 처리

- 입력·처리: 기동 시 UTF-8 파일을 행 단위로 파싱 — `ID, 이름, 나이, 성별, 연봉`
- 정상 행: 메모리 적재
- 자료구조: `List` → 파일 순서·페이지·검색 / `Map` → ID 조회
- 행 파싱 실패: 해당 행만 실패, 행 번호·사유 로그 기록, 원문과 함께 실패 데이터 보관, 다음 행 계속 처리
- 파일 I/O 실패: 원인·stack trace는 서버 로그에 기록, HTTP 응답에 내부 정보 비노출

## 4. 재적재 및 설계 선택

- 방식: 기존 데이터를 먼저 수정하지 않고, 새 파일을 모두 읽은 뒤 사용자·실패 목록을 함께 교체
- 읽기 실패: 기존 사용자·실패 목록 모두 유지
- 조회 일관성: 부분 갱신 상태 비노출 / 동시 재적재: 순차 처리

| 선택 | 이유 | Trade-off · 재검토 조건 |
| --- | --- | --- |
| 파일 전체를 새 스냅샷으로 교체 | 전체 재적재 중 부분 상태 노출을 방지하고, 파일 읽기 실패 시 기존 데이터 유지 | 재적재 중 기존·신규 데이터가 함께 존재. 데이터 규모가 커지면 메모리·GC 비용을 측정하고 저장·갱신 방식 재검토 |
| List + Map 병행 | 파일 순서·페이지 처리와 빠른 ID 조회를 함께 지원 | ID 인덱스용 메모리가 추가됨. 전체 데이터와 인덱스가 메모리 예산을 넘으면 저장 방식 재검토 |
| 이름 검색은 전체 순회 | 별도 인덱스 없이 부분 문자열 검색을 구현 | 데이터·검색 요청량에 따라 비용 증가. 응답 지연이 문제가 되면 부분 검색에 맞는 인덱스나 검색 저장소 검토 |

## 5. 주요 정책

- 중복 ID: 첫 정상 행 유지, 이후 중복 행은 실패 데이터로 기록
- 페이지: 0부터 시작, 기본 `page=0`·`size=20`, 최대 `size=100`, 범위 밖은 빈 목록
- 검색: 앞뒤 공백 제거·대소문자 구분, 빈 검색어는 400, 결과 없으면 빈 배열
- 빈 파일·모든 행 실패: 새 결과로 교체, 사용자 목록은 비워짐
- 파일 읽기 실패: 최초 적재는 기동 실패 / 재적재는 503·기존 데이터 보존

## 6. 테스트

```bash
./gradlew test        # 전체 테스트
./gradlew clean build # 전체 테스트·포맷 검사·실행 JAR 생성
```

- 파일 처리: 파싱·중복 ID·오류 로그
- 조회/검색/페이징: 조회 일관성·검색·페이지 경계
- 재적재: 빈 파일·전체 행 실패·파일 읽기 실패
- HTTP 오류: 잘못된 입력·없는 사용자·파일 읽기 실패·예상 밖 오류
- 동시성/데이터 보존: 동시 재적재 직렬화·실패 시 기존 데이터 유지
- 테스트 데이터: 별도 fixture·임시 파일 사용, 실행용 `user.txt` 변경 없음

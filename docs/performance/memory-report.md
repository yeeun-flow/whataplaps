# 파일 적재·재적재 메모리 측정

측정일: 2026-10-07. 측정 대상: `3a9f562`의 production 코드.

## 결과와 판단

- 정상 100만 행은 모든 요청이 성공했지만, 512MiB heap에서 관측 최대 약 511MiB 및 Full GC 13~14회 발생. 이 조건을 여유 있는 지원 범위로 판단하지 않음.
- 정상 10만 행은 관측 최대 184~224MiB, Full GC 0회. 다만 이름에 한글 512자를 추가한 10만 행은 437~442MiB까지 증가. 행 수만으로 용량을 제한할 근거는 부족함.
- 과제 규모에는 현재 전체 스냅샷 교체 구조를 유지. 실험 결과만으로 새로운 파일 크기·행 수 제한을 API 정책에 추가하지 않음.
- 대용량 지원이 필요하면 입력 바이트 수·행 수·한 행 길이·실패 원문 보관량과 동시 요청량을 함께 정하고 재측정. 메모리에 들어오지 않는 규모는 DB/디스크에 나눠 적재한 후 완료된 버전으로 전환하는 구조 검토.
- 이번 변경은 측정 스크립트와 기록 추가. production 코드·API 계약·GC 운영 설정 변경 없음.

| 항목 | 조건 |
| --- | --- |
| 장비 | Apple M2, 논리 CPU 8개, RAM 16GiB |

| 요청 순서 | 최초 적재 확인 → reload 1회·조회 50회 워밍업 → 단독 조회 100회 → 단독 reload 3회 → 조회 병행 reload 3회 |
| 병행 조회 | `GET /users?page=0&size=20`, 클라이언트 1개, 응답 후 50ms 대기 |

- 정상 입력: 고유 ID, `사용자{id}`, 나이 30, 성별 M, 연봉 `30_000_000`.
- 실패 10%: 매 10번째 행의 연봉을 `bad`로 변경. WARN 로그를 끄지 않고 파일에 기록.
- 긴 이름: 정상 10만 행의 각 이름 뒤에 한글 `가` 512자 추가. ID·성별·연봉 등은 동일.
- 기존 스냅샷과 새 스냅샷이 겹치는 reload를 측정. 각 JVM은 기동 적재 1회와 reload 7회 수행.
- 제공 원본 `user.txt`와 사용자의 기존 서버는 변경하지 않음.

## 적재·메모리·GC 결과

`A / B`는 독립 실행 결과. MiB는 1,048,576바이트. reload 시간은 단독 호출 3회의 중앙값이며 HTTP 왕복을 포함함.

| 입력 | 파일 MiB | 기동→조회 가능 ms A/B | reload 중앙값 ms A/B | 관측 최대 heap MiB A/B | Full GC 횟수 A/B | 최대 GC 정지 ms A/B |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 빈 파일 | 0 | 2,999 / 2,164 | 1.2 / 1.2 | 149.0 / 147.8 | 0 / 0 | 10.8 / 10.3 |
| 정상 1만 | 0.33 | 4,508 / 2,131 | 29.0 / 23.3 | 156.2 / 157.2 | 0 / 0 | 45.5 / 10.8 |
| 정상 10만 | 3.51 | 3,446 / 2,458 | 320.8 / 144.3 | 223.9 / 184.0 | 0 / 0 | 92.6 / 19.6 |
| 정상 100만 | 36.98 | 5,401 / 3,478 | 2,316.7 / 2,406.3 | 510.5 / 510.8 | 14 / 13 | 409.1 / 384.3 |
| 10만·실패 10% | 3.44 | 4,227 / 4,148 | 238.4 / 230.5 | 230.1 / 219.8 | 0 / 0 | 23.3 / 25.0 |
| 10만·긴 이름 | 149.99 | 4,440 / 3,942 | 590.5 / 488.1 | 436.5 / 442.0 | 0 / 0 | 35.5 / 38.6 |

- 전체 12회 실행에서 정상 응답 및 기대 건수 확인. OOM으로 종료된 정식 실행 없음.
- 관측 최대 heap은 전체 실행(기동·워밍업·조회·reload)을 포함한 `jstat` 표본 중 최댓값. 정확한 순간 최대치나 reload만의 최대치가 아님.
- `S0U + S1U + EU + OU`를 합산. Metaspace·스레드 스택·JFR 버퍼 등 heap 밖 메모리를 포함하지 않으며 프로세스 RSS와 다름.
- 파일 크기와 heap은 비례 계수가 일정하지 않음. 객체·키·인덱스·임시 컬렉션 및 문자열 표현 비용이 추가됨.
- 빈 파일의 관측 최대도 약 149MiB. 프레임워크/JFR/요청 처리의 일시적 할당이 포함되므로 이 수치를 상주 데이터 크기로 해석하거나 다른 시나리오에서 단순 차감하지 않음.

## reload 중 조회 영향

| 입력 | 병행 reload 중앙값 ms A/B | 단독 조회 최대 ms A/B | 병행 조회 수 A/B | 병행 조회 최대 ms A/B |
| --- | ---: | ---: | ---: | ---: |
| 빈 파일 | 1.2 / 1.3 | 1.9 / 2.7 | 1 / 1 | 1.3 / 1.1 |
| 정상 1만 | 18.2 / 17.2 | 4.0 / 2.5 | 1 / 1 | 2.4 / 2.0 |
| 정상 10만 | 160.8 / 128.4 | 5.2 / 3.3 | 9 / 7 | 4.4 / 4.2 |
| 정상 100만 | 2,301.9 / 2,638.2 | 14.3 / 8.7 | 96 / 102 | 407.3 / 344.7 |
| 10만·실패 10% | 250.9 / 270.3 | 3.4 / 2.9 | 13 / 15 | 10.3 / 4.8 |
| 10만·긴 이름 | 488.4 / 561.7 | 4.4 / 3.8 | 26 / 29 | 5.0 / 5.6 |

- 단독 조회는 실행별 100회. 병행 조회는 reload가 실행되는 구간에 클라이언트 루프를 병행한 결과이며, 모든 조회가 실제 파싱 구간과 겹친다고 보장하지 않음.
- 작은 입력은 reload가 짧아 조회 표본이 1개뿐임. 안정적인 지연 상한이나 백분위 판단에 사용할 수 없음.
- 정상 100만 행은 조회 메서드가 reload의 락을 잡지 않아도 수백 ms 지연이 관측됨. GC 정지·CPU 경합 등의 영향을 받으므로 불변 스냅샷이 무지연 조회까지 보장하지는 않음. 개별 요청 지연의 원인을 GC 하나로 단정하지 않음.
- 단독 호출과 병행 호출 순서가 고정되어 JIT·캐시·GC 상태가 다름. 병행 시 중앙값이 더 낮더라도 동시 조회가 성능을 개선했다고 해석하지 않음.

## GC 후 사용량과 해석 한계

아래는 JFR의 **마지막 `After GC` 이벤트**에서 관측한 heap 사용량. 이벤트는 마지막 reload 완료 전일 수 있고, 전체 생존 객체만 남기는 Full GC 결과라는 보장도 없음.

| 입력 | 마지막 GC 후 heap MiB A/B |
| --- | ---: |
| 빈 파일 | 18.7 / 18.3 |
| 정상 1만 | 19.2 / 20.2 |
| 정상 10만 | 147.2 / 148.0 |
| 정상 100만 | 378.0 / 400.7 |
| 10만·실패 10% | 98.9 / 107.8 |
| 10만·긴 이름 | 263.5 / 284.0 |

- 이 수치로 메모리 누수 유무나 스냅샷 단독 크기를 결론 내리지 않음. 강제 GC는 사용하지 않았으며 장시간 반복 적재 시험도 수행하지 않음.
- 테스트 장비에서 다른 프로그램이 함께 실행됨. 결과는 운영 환경의 처리량/SLO 보장이 아님.
- 이름 검색 전체 순회, 실패 목록 전체 응답, 여러 동시 클라이언트, 매우 긴 단일 행, 파일 외부 수정, 크기가 증가하는 파일 교체는 이번 실험 대상에서 제외.
- 최초 적재 시간은 JVM 시작부터 실제 조회 건수 확인까지이며 순수 `load()` 시간과 다름. 100ms 준비 확인 주기와 JVM/JFR/Spring 초기화 시간이 포함됨.
- 현재 로더 완료 로그는 스냅샷 생성·교체 전에 출력됨. 시험 실행에서 로그 직후 빈 조회 응답을 관측해, 측정 스크립트는 기대 건수가 실제 조회될 때까지 대기하도록 구성. 기동 중 요청 허용 여부는 별도 검토 대상이며 이번 측정에서 production 동작을 변경하지 않음.
- 시험 실행의 통계 파싱/준비 확인 문제를 보완한 뒤 두 번 재측정한 A/B만 수록.

## 재현

프로젝트 루트에서 Java 21과 Python 3 사용. 실행 결과 디렉터리는 기존에 없어야 함.

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
./gradlew clean build
python3 scripts/measure_memory.py --output /tmp/whatap-memory-a
python3 scripts/measure_memory.py --output /tmp/whatap-memory-b
```

한 시나리오만 실행:

```bash
python3 scripts/measure_memory.py \
  --output /tmp/whatap-memory-100k \
  --cases normal-100k
```

- 스크립트: [measure_memory.py](../../scripts/measure_memory.py)
- 집계값·호출별 시간·GC 후 사용량·JAR SHA-256: [memory-results.json](memory-results.json)
- 생성되는 `user.txt`, 애플리케이션/GC 로그, `jstat.txt`, JFR은 지정한 외부 디렉터리에 저장. 저장소에는 포함하지 않음.
- 실제 원시 측정 경로: `/tmp/whatap-memory-20261007-run2`, `/tmp/whatap-memory-20261007-run3`. 임시 파일이므로 장기 보관은 보장하지 않으며, 재현 스크립트와 집계 JSON을 함께 제출.
